# Election Outcome Report — Concrete Blockchain-Backed Simulation

This report is the concrete complement to `EXPERIMENTAL_REPORT.md`.
Where that report evaluates the *abstract probability* that a
manipulation threshold `m` is reached (`P(X>=m)`), this report answers
a more direct question: **does the attack actually change who wins a
real, blockchain-recorded election, and does the countermeasure
actually stop it?**

Every number below is generated by `python run_election_attacks.py
--trials 300 --seed 42`, which:

1. Builds a genuine proof-of-work blockchain for each trial
   (`blockchain_core/chain.py` — real SHA-256 mining, real nonce
   search, real chain linkage).
2. Casts a synthetic electorate's legitimate ballots and mines them
   into the chain.
3. Reads the pre-attack winner **directly from the mined chain**
   (`Blockchain.count_votes()`), not from a running Python total.
4. Runs bribery / Sybil / ballot-stuffing attacks against the
   *currently losing* candidate, under both a baseline and a
   protected security configuration.
5. Mines only the fraudulent votes that survive both the
   acceptance gate and the detection gate into a new block.
6. Reads the post-attack winner from the chain again, and re-validates
   the entire chain's integrity.

Source of truth: `results/csv/election_outcome_results.csv` (1,800
rows: 300 trials x 3 attack types x 2 system configurations) and
`results/json/election_outcome_summary.json`.

---

## Headline result

| Attack | Baseline flip rate | Protected flip rate | Absolute reduction | Relative reduction |
|---|---|---|---|---|
| Bribery | 44.0% | 1.3% | 0.427 | 97.0% |
| Sybil | 54.7% | 11.3% | 0.433 | 79.3% |
| Ballot stuffing | 55.0% | 8.3% | 0.467 | 84.8% |

In the **baseline** configuration, an attacker flipped the outcome of
a close, otherwise-legitimate election in 44-55% of the 300 tested
scenarios, across all three attack types. Under the **protected**
configuration, the flip rate fell to 1.3-11.3% -- bribery in
particular became almost entirely infeasible (a 97.0% relative
reduction), because raising the detection probability `q` directly
suppresses the number of bribed votes that survive to be counted,
compounding with the rational-voter gate that already filters out
unprofitable bribe offers.

**Blockchain integrity was never violated by a successful attack**:
`chain_valid_after_attack` was `True` for all 1,800 rows
(`results/json/election_outcome_summary.json::chain_integrity_never_violated`).
This is expected and important to state precisely: attacks succeed or
fail *at the validation gate before mining* (a fraudulent vote either
passes acceptance+detection and is mined, or it doesn't and never
reaches the chain) -- the chain itself is never corrupted after the
fact. Corrupting already-mined history is a *different* attack
(tampering), and is demonstrated separately and successfully detected
in `demo_blockchain_evoting.py`'s Phase 1 demo (see
`results/BLOCKCHAIN_EVOTING_DEMO_LOG.md`) -- tampering with a
previously mined block's vote data is caught immediately by
`is_chain_valid()`, with the exact block index identified.

## How each attack affects the scenario

**Bribery (Figure 5; representative example described below).** In a representative
flipped example (trial 1, N=703 legitimate voters, pre-attack tally
359-344 in favour of Candidate A), the baseline attacker bribes enough
voters that Candidate B's tally jumps from 344 to 659 -- comfortably
overtaking A. Under the protected configuration, the same underlying
election and attacker resources yield zero net gain for B (tally stays
at 344): every bribe attempt that gets made is either rejected by the
rational-voter gate (`Uv<=0`, since detection risk `q` is much higher)
or is accepted but then caught by the detection pipeline before its
vote is mined.

**Sybil (Figure 5; representative example described below).** For the identical starting
election, baseline Sybil identities push B's tally from 344 to 400 --
still enough to overtake A's 359. Protected configuration limits the
gain to 354 -- just short of the 360 needed, so the legitimate winner
holds.

**Ballot stuffing (Figure 5; representative example described below).** Baseline pushes B to 395
(flip); protected limits it to 358 (no flip, by a single vote in this
particular example -- illustrating that even "close calls" under
protection tend to fall on the side of the legitimate result across
the full 300-trial distribution, per the 8.3% residual flip rate).

## How countermeasures tackle each attack, concretely

The countermeasure pipeline modelled here (`simulate_fraud_attempts`
in `models/evoting_system.py`) mirrors the validation pipeline
described in the project's blockchain design: **submit -> acceptance
check -> detection check -> blockchain recording**. Concretely:

- **Bribery:** raising `q` (detection probability) has a *double*
  effect -- it (a) makes bribery less rationally attractive to voters
  in the first place (`Uv=(1-q)R-qP` falls, per `mathematics/utility.py`),
  and (b) increases the chance any bribe that *is* accepted is still
  caught before its vote is mined. This compounding is the likely
  explanation for bribery's unusually large 97.0% relative reduction
  in flip rate, compared with its 81.9% reduction in the abstract
  P(X>=m) metric reported in `EXPERIMENTAL_REPORT.md` -- flipping a
  *specific, already-close* election is a stricter bar than merely
  reaching an arbitrary threshold `m` on average.
- **Sybil / ballot stuffing:** raising `pd`/`pb` (detection) and
  lowering `qs`/`qb` (acceptance) both shrink the surviving fraud
  count directly; only surviving (accepted-and-undetected) fraudulent
  votes are ever mined into the chain, so the countermeasure's effect
  is visible immediately in the post-attack tally, not just in an
  abstract probability.
- **The blockchain's role specifically:** the ledger does not decide
  whether a vote is fraudulent -- that is the acceptance/detection
  pipeline's job, representing signature verification, identity
  checks, and duplicate/eligibility validation. The blockchain's
  contribution is to make whatever *was* accepted immutable and
  auditable: once mined, a legitimate result cannot be silently
  altered without every subsequent block's hash linkage breaking,
  which `is_chain_valid()` catches deterministically (demonstrated in
  `demo_blockchain_evoting.py`).

## Threats to validity specific to this concrete simulation

- Only one representative flipped example per attack type is described
  below (chosen as the first flipped baseline trial found); the
  full 300-trial distribution (flip rates above) is the basis for all
  headline claims, not this single illustrative example.
- Elections are two-candidate and support is sampled close to 50/50
  (35-65%) specifically to produce a meaningful proportion of "close"
  races worth attacking -- a landslide election is realistically much
  harder to flip regardless of security configuration, so these flip
  rates should be read as conditional on "the race was close enough to
  be worth attacking," not as an unconditional statement about all
  possible elections.
- Attacker resource parameters (`B`, `R`, `P`, `S`, `A` and the
  baseline/protected `q`/`qs`/`pd`/`qb`/`pb` ranges) are drawn from the
  ranges in `simulation/election_attack_runner.py`, chosen to be
  broadly consistent with (but not identical to) the ranges in
  `config.py` used for the abstract 2,500-trial simulation; see that
  module's docstring for the exact values.
- Difficulty is set low (`difficulty=3`, i.e. 3 leading hex zeros) so
  that mining hundreds of trials completes in about a minute; this
  does not change the correctness of the tamper-detection or
  chain-validity properties demonstrated, only the computational cost
  of finding a valid nonce.
